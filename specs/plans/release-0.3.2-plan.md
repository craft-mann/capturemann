Original heading: In-app update with Velopack (added Nov 11, 2026): analysis and plan

Sources read Nov 11, 2026: docs.velopack.io (introduction, Rust, Windows, macOS, Linux, distributing) and docs.rs/velopack (crate 1.2.161 dated Sep 29, 2026, MIT). Items marked **verify** were not stated by those pages and need the spike below.

**What Velopack is.** An installer and updater framework. The app links a client library (Rust crate `velopack`), calls `VelopackApp::build().run()` first in `main()`, then `UpdateManager::new(source, None, None)`, `check_for_updates()`, `download_updates()`, `apply_updates_and_restart()`. The `vpk` tool (needs the .NET 8 SDK, CI only, never shipped) packs a release folder into installers, full packages, optional delta packages and a feed `releases.<channel>.json`, which can live on any static host or GitHub Releases. Feed entries list file name, size, type (Full or Delta) and a SHA1 hash.

**What it changes per platform**
- **Windows:** `Setup.exe`, one click, per user, no elevation, installs to `%LocalAppData%\<id>` with `current\` (the whole folder is replaced on every update), `Update.exe` and a stub exe. Signing is "very recommended, not required". Locked files: the updater kills processes in `current`, or asks the user. Today we ship an NSIS per-user installer (`packaging/windows/installer.nsi`, `%LOCALAPPDATA%\Programs\CaptureMann`, optional PATH, winget manifest). Velopack would replace NSIS as the installer (or the two coexist, which is worse).
- **macOS:** `.app` (an `.app` folder is used as is), `.pkg` and `.zip`; signing and notarization are required; the `.app` is self-contained and updates in place, with an AppleScript elevation prompt when it sits in `/Applications`; App Sandbox is not supported (we do not use it). **verify:** wrapping our own signed and notarized `.app` and keeping our DMG as the first-install format; one feed per CPU (arm64 and Intel); the Screen Recording and Microphone permission grants surviving an update (same Developer ID and bundle id should keep them; the Oct 23, 2026 note on a bundle swapped under a running copy shows this is the highest-risk check).
- **Linux:** only an `.AppImage`, no deb or rpm. We ship a tarball, a `.deb` and an APT repository, and Ubuntu 24.04 has no `libfuse2` by default. **Recommendation: no Velopack on Linux.** APT is the update path there; the app shows a notify-only message with the `apt` command.

**Conflicts with decisions already taken**
1. **Maintainer decision, Oct 25, 2026 (plan.md M7): no update code and no network call from the app; an opt-in "Check for updates" may come later.** NFR-9 (no network call unless the user enabled a destination, publish target or AI key) and the README promise "no telemetry, no network traffic unless you connect a destination or download a model". This request reverses the decision, so the design must be **opt-in and say exactly what is sent** (one HTTPS GET of the feed file; the host sees the IP and a user agent; no identifier, no usage data; **verify** by reading the crate source and a packet capture).
2. **Update integrity (NFR-15 says "auto-update with signature check").** Velopack relies on the OS code signature plus the feed hash (SHA1 listed; **verify** whether the crate also checks SHA256 or anything stronger). macOS is covered by Developer ID and notarization. **Windows is unsigned today**, so an auto-applied update would rest on HTTPS and a hash served from the same place. Options: (a) make Windows signing (SignPath, see `docs/development/windows-signing-options.md`) a prerequisite for "Apply" on Windows; (b) verify a detached minisign signature of the package (we already have `packaging/linux/minisign.pub` and `sign-linux.sh`) before `apply`, if the API lets us hold the apply step; (c) notify-only on Windows until signed. Recommendation: (b) if the spike shows the download and apply steps are separable, else (c).
3. **Every user-facing action needs an MCP tool and CLI command with identical behavior (CLAUDE.md).** `check_for_updates` is a read (Free, network) and gets a tool and `capturemann update check`. `install_update` restarts the app and replaces files: **Confirm tier**, refuses with `busy` while a recording, a running job or an agent call is active, never exposed as Free; the CLI has `capturemann update install`. New app-only settings `updates.*` (not writable through `set_settings`).
4. **`cargo deny` and licences.** The crate is MIT, but its dependency tree (zip, compression, HTTP) may bring licences we kept out on purpose (bzip2-1.0.6, CDLA-Permissive-2.0; see CLAUDE.md on the vendored sherpa crates). **Verify first** with `cargo deny check` on a scratch branch; if it fails, vendor a trimmed copy as for sherpa or drop to the fallback below.
5. **Hosting and pre-releases.** `releases/latest/download/<file>` skips pre-releases and all 0.3.x releases are pre-releases. Use a dedicated release, for example tag `updates` (like the `apt` release), whose assets `vpk` replaces each release; or craftmann.app static hosting. Feed and packages must sit in the same folder.
6. **Other install channels.** A Homebrew cask, winget and APT install must not self-update behind their package manager. The app detects "installed by Velopack" (**verify** the Rust API for it); every other case (zip, brew, winget on the old installer, dev bundle, Linux) shows the state "updates are managed by <brew, winget, apt or you>" with the download link, and never offers Apply.
7. **Processes.** The CLI, MCP server, daemon and overlay all live in the install folder, and Claude Desktop's MCP config points at `cm-mcp` there. An update kills or restarts them: the Confirm dialog says so, and the app refuses while an agent call or a recording runs.
8. **Existing users cannot update into Velopack.** 0.3.1 users (NSIS, DMG, brew) install the 0.3.2 Velopack build by hand once; the first real in-app update is 0.3.2 to the next version. The 0.3.2 release text says so, and the winget and Homebrew manifests change installer type and name.

**Cheaper fallback if the spike is red:** an opt-in "Check for updates" that only compares the running version with the feed (or the GitHub releases API) and shows the download link, on all three systems; no packaging change; same settings, tool and CLI. Ship that in 0.3.2 and Velopack Apply in 0.3.3.

**Spike result, macOS (Nov 11, 2026; report `docs/development/velopack-spike-0.3.2.md`, branch merged; Windows spike still running).** Recommendation of the agent: GO WITH CHANGES; becomes NO-GO if the permission-survival check fails. Findings that change the plan:
- **A stock client is not private enough.** `HttpSource` requests `releases.<channel>.json?localVersion=...&id=<app id>&stagingId=<random uuid>` with user agent `ureq/3.5.1`. We would write our own `UpdateSource` (the trait is public) that sends nothing but the feed URL; it can also verify our minisign signature on every download and delta, which the stock client does not do (it checks only SHA-256, or SHA-1 when the feed has none; a delta-rebuilt package is never checked against the feed hash).
- **`cargo deny` fails on three packages of the tree:** `webpki-roots` (CDLA-Permissive-2.0, the licence we kept out on purpose; comes from the default `rustls` feature of `ureq`), `derivative` (RUSTSEC-2024-0388, unmaintained), `zip` 8.6.0 (RUSTSEC-2026-0367, not reachable for us; velopack 1.3.39 asks for `zip ^9.0.3`, not built). Needs decisions: vendor a trimmed crate as for sherpa, a new `deny.toml` exception, or the fallback.
- **`VelopackApp::build().run()` applies a pending package and relaunches just by running `version`** and drops the environment (`CAPTUREMANN_*` lost). Call it only in `cm-desktop`, with `set_auto_apply_on_startup(false)`.
- **Signing:** vpk adds `UpdateMac` (7.7 MB) and `sq.version` to the `.app`, so it must re-sign: `--signAppIdentity <id> --signDisableDeep --signEntitlements packaging/macos/CaptureMann.entitlements` kept our two entitlements on a copy (ad hoc identity only; a Developer ID was not used). Our `notarize.sh` stays in charge (sign with vpk, build the DMG from vpk's `.app`, notarize the DMG). Not run: `--notaryProfile`.
- **Size and cadence:** full package 88.9 MB, DMG 87.0 MB, delta 0.2.9 to 0.3.1 only 22.3 MB; the first update after a DMG install is always a full download.
- **Detection and migration:** `UpdateManager::new` returns `Err(NotInstalled)` outside an updatable `.app`; 0.3.1 DMG installs cannot self-update; arm64 and Intel need separate channels and feeds (`osx-arm64`, `osx-x64`).
- **Apply behaviour:** 0.7 s down for a small app, 1.4 to 1.9 s for 190 MB; a first launch of a never-launched 190 MB ad-hoc bundle took 27 to 30 s (not diagnosed; needs a notarized build); old processes of the same `.app` and their children keep running through an apply (the app must stop its own helpers first); read-only location fails and relaunches the old version; truncated, corrupt or wrong-hash packages fail cleanly and are never applied; there is no default HTTP timeout (set one).
- **Hosting:** use a release tagged `updates` with one feed per channel; `latest/download` does not discriminate today because v0.3.1 is a normal release.
- **Fallback D (notify-only) is about 150 to 250 lines:** one signed `latest.json` on the `updates` release, `semver` (already in `Cargo.lock`), the `minisign-verify` crate; it adds none of the failing crates.
- **Maintainer must:** run the permission-survival check on a Developer ID signed and notarized pair of builds with the real bundle id (exact vpk command and seven steps in the report; back up `/Applications/CaptureMann.app` first) and confirm Gatekeeper and first-launch time on that build.
- **Not verified:** HTTPS through `ureq`, the 1.3.39 client, notarization, a real Developer ID re-sign, Intel, a real packet capture, `cm-desktop` with the crate linked.

**Orchestrator's read:** Velopack Apply on macOS is doable but needs a custom source, vendoring or exceptions in `deny.toml`, vpk signing flags, a stop-helpers step and a Developer ID test, i.e. more than fits next to the other 0.3.2 work. Proposal: ship fallback D in 0.3.2 (opt-in, signed `latest.json`, same settings, tool and CLI as designed) and keep Velopack Apply for 0.3.3 once the permission check and the Windows spike are in. Final call after the Windows spike report.
