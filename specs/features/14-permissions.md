# Permissions (PRM)

The operating-system permissions CaptureMann can use, shown in one place with their live state and a button that fixes each one. The product maintainer's rule (Oct 21, 2026): the user may not know which permissions the app needs, so the app asks actively, never silently, and always says what is granted and what is not. Visual reference: the kit is silent (no permissions screen); the cards follow the Settings cards and status pills (DESIGN §5.8, §5.10).

### PRM-1 Permissions
**Priority** P0 · **Status** In progress (built on macOS: the permissions module with non-prompting checks, the in-app setup screen, Settings → Permissions, the banner, toasts and entry points, just-in-time requests; logic tested with a fake provider, the real OS dialogs and panes were not exercised in testing and there is no stored hardware run of `tests/manual/PRM-1.md`; mid-recording revocation is built and tested with fakes only (AC13), never run on a Mac; Windows rows are compile-only) · **Crates** apps/desktop (`permissions`, setup screen, Settings → Permissions), cm-capture, cm-audio, cm-camera, cm-cursor (non-prompting checks) · **Depends on** CAP-1, REC-1, CAM-4, AUD-1, DESIGN §5.8

**User story** — As a new user, I want CaptureMann to tell me which permissions it needs and why, show which ones are granted, and give me a button for each missing one, so that captures and recordings work without me guessing at System Settings.

**Description**
- **What is listed (macOS).** *Screen Recording* (required: screenshots, recording, the capture overlay; system audio uses this same permission, so it has no row of its own); *Microphone* (optional: voice track); *Camera* (optional: webcam bubble and camera track); *Input Monitoring* (optional: cursor clicks and scroll in recordings; without it only the cursor position is recorded). Accessibility is not listed: the global shortcuts use Carbon hot keys and the cursor track a listen-only event tap, so nothing needs it. Notifications are not listed (the app posts no OS notifications); "Launch at login" is a preference (a LaunchAgent for installed bundles, default off), not a permission.
- **What is listed (Windows, compile-only).** *Microphone* and *Camera*, each with "Open Settings" (`ms-settings:privacy-microphone`, `ms-settings:privacy-webcam`), and the note that screen capture needs no permission.
- **A card** (kit card, status pill) per permission: name, a "Required" or "Optional" pill, the state pill, one plain sentence saying why, a "Needed for:" line naming the features, an extra sentence for states that need one, and the buttons.
- **States.** *Granted*; *Granted — restart required*; *Not granted* (Screen Recording and Input Monitoring: macOS cannot tell never-asked from denied without prompting); *Not asked yet* (Microphone, Camera); *Denied*; *Restricted by policy* (MDM, Screen Time); *Checking…* before the first read. All reads use non-prompting checks (`CGPreflightScreenCaptureAccess` through cm-capture, `microphone_permission`, `check_camera_permission`, `cm_cursor::preflight`).
- **Buttons.** *Grant access…* calls the OS request API (Screen Recording `CGRequestScreenCaptureAccess`, Input Monitoring `CGRequestListenEventAccess`, Microphone and Camera their authorization requests) and is shown for *Not asked yet* and, for Screen Recording and Input Monitoring, for *Not granted* (macOS shows its dialog once; later calls only add the app to the list). *Open System Settings* opens the exact pane: `x-apple.systempreferences:com.apple.preference.security?` + `Privacy_ScreenCapture`, `Privacy_Microphone`, `Privacy_Camera` or `Privacy_ListenEvent`. It is the only action for *Denied* and *Restricted*. *Restart CaptureMann* replaces both for *Granted — restart required*.
- **Where it shows.** Settings → Permissions (also from the tray "Permissions…", the launcher command "Permissions…", the library banner, the Record sheet and the "Open Permissions…" button of the "Capture didn't start" and "Recording didn't start" toasts); the setup screen (revised Oct 21: a screen of the main window, no popup); a banner at the top of the library while Screen Recording is missing; the Record sheet.
- **Setup screen (revised Oct 21, 2026: replaces the first-run popup window; the main window shows it, see AC12).** Title "CaptureMann needs a few permissions", the cards, "Not now" and "Continue", in the content area of the main window (sidebar dimmed). Shown on the first launch and on every launch where a required permission is missing. It re-reads the states every second while showing. "Continue" is enabled once every required permission works, records that the screen was seen and goes to the library. When Screen Recording was granted while the process was running (it started without it), "Restart CaptureMann" is the primary action: it quits and a small script waits for the old process to exit (it may be saving a recording for up to 10 s, so the two never overlap) and then runs `open -n` on its own `.app`; a copy that does not run from a `.app` shows a toast with instructions instead.
- **First-run rule (revised Oct 21, 2026, supersedes "opens on the first launch" above).** At startup the main window opens on the setup screen only if Screen Recording (required) is not granted, or it is the very first launch (`permissions.onboarded` unset) and at least one listed permission, required or optional, is not granted or not asked yet. With everything granted it is never shown, no banner shows, and `permissions.onboarded` is set silently. While showing it re-reads every second; once every permission is granted it shows "All set" and moves on to the library after about 1 s, and records onboarded. With only optional ones missing it stays until "Continue" or "Skip optional". Leaving it ("Not now", or clicking another sidebar item) dismisses it for this launch and records onboarded unless a required permission is missing, so only a missing required permission brings it back next launch; optional ones are surfaced just in time and in Settings → Permissions, which has a "Reopen setup" button that shows the screen again. A `--background` or login launch opens no window, except when the setup screen is due (a required permission is missing): then the main window opens on it. Cause of the earlier bug: the rule opened the popup on every launch until "Continue" was pressed, whatever was granted, and "Not now" or X never recorded anything.
- **Restart logic.** A process remembers whether Screen Recording was granted when it first looked. If it was not and the preflight later turns true, the row reads *Granted — restart required*, because macOS usually keeps refusing capture to a process that was already running. CaptureMann cannot probe whether a particular process is affected, so the copy says "usually" and treats the row as not yet usable (the banner stays, "Continue" stays off).
- **Just in time.** Turning the camera or the microphone on in the Record sheet asks the OS first when the state is *Not asked yet*, then reads the devices again. A denied permission is not asked again; its note in the sheet offers "Open System Settings". Recording starts without a camera or microphone that is blocked (CAM-4.AC3).
- **One instance.** CaptureMann holds an exclusive lock (`instance.lock` in the config directory) for its whole life; a second launch asks the first to show itself and exits, so two copies never fight over the hotkeys, the tray, the job worker or the socket.
- **Never silent.** Nothing calls a request API at startup, when a window opens, or while polling. Only a button press, or the toggle of a feature that needs the permission, does.
- **Record sheet.** A failed display listing is shown as such (REC-1): `permission_missing` → "Screen Recording permission is missing", "After granting, quit and reopen CaptureMann.", Open System Settings, Grant access…, Open Permissions…, Start disabled. Any other error code shows the daemon's own message with Retry. "No display found" is reserved for a successful listing with zero displays.

**Acceptance criteria**
- **AC1** (met by unit test `prm1_lists_what_the_os_needs`) Given macOS, then the page lists Screen Recording (Required), Microphone, Camera and Input Monitoring (Optional), each with why and which features; Accessibility and Notifications are not listed. On Windows only Microphone and Camera are listed.
- **AC2** (met by unit tests with a fake provider: `prm1_provider_transitions_and_never_silent`; the pill rendering and the 1 s and 2 s refresh loops are unverified) Given a permission changes in System Settings, then its state pill follows within 2 s while Settings → Permissions or the setup screen is showing.
- **AC3** (action matrix met by unit test `prm1_action_matrix`; the real OS dialogs were not triggered in testing) Given Microphone or Camera is *Not asked yet*, or Screen Recording or Input Monitoring is *Not granted*, then "Grant access…" is offered first and calls the request API; for Microphone and Camera it is not offered once they are *Denied* or *Restricted*.
- **AC4** (links met by unit test `prm1_deep_links`; opening the real panes unverified) Given a permission is *Denied*, *Restricted* or *Not granted*, then "Open System Settings" opens its pane via the deep links above.
- **AC5** (revised Oct 21: screen, not window) (rule met by unit tests `prm1_first_run_rule` and `prm1_required_vs_optional_gating`; screen rendering checked on the fake provider only) Given the first launch, or a launch where Screen Recording is missing, then the main window opens on the setup screen (AC5 originally required a separate window: superseded by AC12); "Continue" is enabled only when every required permission works; optional permissions never gate it; a returning user with everything granted sees no setup screen.
- **AC6** (logic met by unit test `prm1_restart_required_logic`; whether a restart is really needed on a given machine is unverified) Given Screen Recording is granted in System Settings while CaptureMann runs without it, then the row reads *Granted — restart required* and "Restart CaptureMann" relaunches the bundle.
- **AC7** (rule met by unit test `prm1_just_in_time`; the sheet wiring has no automated test) Given Camera or Microphone is *Not asked yet*, when the user turns it on in the Record sheet, then the OS dialog is requested at that moment and the sheet reloads its devices.
- **AC8** (probing never requests: unit test `prm1_provider_transitions_and_never_silent`) Given the app starts, a screen opens or the page refreshes, then no request API is called.
- **AC9** (banner condition met by unit tests `banner_condition` in `permissions` and the sheet tests `rec1_permission_missing_is_not_no_display_found`, `rec1_other_errors_show_the_message`, `rec1_no_display_found_only_for_an_empty_success`; toasts and the tray and launcher entries have unit tests for their action, the rendering was checked on the fake provider only) Given Screen Recording is missing, then the library shows one non-blocking banner "Screen Recording permission is missing — captures and recording won't work" with its buttons; the Record sheet says the same instead of "No display found" and disables Start; a failed capture or recording start shows its toast with "Open Permissions…".
- **AC10** (not verified: no Windows machine) Given Windows, then Microphone and Camera link to the matching `ms-settings:` pages and no Screen Recording row appears.
- **AC11** (rule met by unit tests `prm1_first_run_rule`, `prm1_auto_close_and_dismiss` and the app tests `startup_route_follows_the_first_run_rule`, `auto_advance_and_dismiss_by_navigation`, `prm1_restart_flag_never_persists`; screen timing, navigating away and "Reopen setup" are checked manually, see `tests/manual/PRM-1.md`) Given all four permissions are granted and `permissions.onboarded` is unset, then no setup screen shows and the flag is set; given Screen Recording is missing, the screen shows on every launch; given only optional ones are missing, it shows on the first launch only and offers "Skip optional"; given everything becomes granted while it is showing, it shows "All set" and goes to the library after about 1 s; leaving it by another sidebar item or "Not now" records onboarded unless Screen Recording is missing; the restart-required state is never stored: a fresh process that sees the grant at start reads *Granted*.
- **AC12** (added Oct 21, 2026; routing met by unit tests `startup_route_follows_the_first_run_rule`, `background_opens_a_window_only_for_the_setup_screen`, `entry_points_map_to_the_permissions_page`; rendering checked on the fake provider and manually, see `tests/manual/PRM-1.md`) No separate window: the setup screen is part of the main window. Given the startup rule says show, the main window opens directly on it (also for `--background` launches, the only case where `--background` opens a window); "Open Permissions…" entries (tray, launcher, banner, toasts, Record sheet) open or raise the main window on Settings → Permissions; no permissions window exists. **Revised Oct 21: in-app screen instead of a popup window.**

**Edge cases and errors**
- Denied earlier → the only button is "Open System Settings" (the OS will not prompt again); the card says so.
- Restricted by policy → the card says only an administrator can allow it; the button opens the pane anyway.
- The bundle's code signature changed (ad-hoc re-sign) → macOS drops the Screen Recording grant; the states read *Not granted* and the cards, banner and sheet note say to switch the CaptureMann entry off and on and restart. A stable identity (`packaging/macos/create-dev-identity.sh`) avoids it.
- The permission is revoked while a recording runs → built Oct 23, 2026, **tested with fakes, never run on a Mac** (AC13). **Decision (the spec was silent):** Screen Recording is the required track, so losing it stops the whole recording cleanly; losing only the Camera or the Microphone does not stop it, because the screen is the product and an optional track is a gap or silence (the same policy as an unplugged camera). Accessibility and Input Monitoring only degrade the cursor track (REC-7.AC4) and never stop anything. Detection is twofold: the track's own typed failure (ScreenCaptureKit `SCStreamErrorUserDeclined` -3801 "user declined TCCs" becomes a `permission_revoked` halt; an `AVCaptureSession` runtime error -11852 becomes a typed camera event) and a once-per-second poll of the non-prompting permission checks (Screen for the screen track, Camera, Microphone), acted on only when it shows on two ticks in a row. The microphone has no typed error (CoreAudio keeps delivering digital silence, which the 15 s `mic_silent` warning also catches). macOS may also end the whole process when the user removes Camera or Microphone access in System Settings; nothing can be done in that case beyond the crash recovery of REC-8, and what the OS does is what the hardware run of `tests/manual/PRM-1.md` (section "Revoked during a recording") must record.
- Opening System Settings fails (no handler) → nothing happens; the user opens it by hand.
- The Microphone or Camera dialog stays unanswered → the button reads "Waiting for the system…" and the request times out after 120 s.
- Unbundled dev run (`cargo run`) → permissions belong to the host terminal, not to CaptureMann; the restart button explains that it cannot relaunch.

**Agent interface** — Not built. A read-only status action (`get_permissions`, Free tier) with a CLI command `capturemann permissions` and an MCP tool would be additive in cm-daemon; it needs AGT-1 parity tests (action, tool and command listed together) and is left for a follow-up. Granting always needs the user at the keyboard, so no agent action can request a permission.

**Out of scope** — Requesting permissions on behalf of an agent, Accessibility (no feature needs it), Notifications, resetting grants with `tccutil`, Linux, detecting per-process "restart needed" beyond the heuristic above.

- **AC13** (added Oct 23, 2026; met by the daemon tests `prm1_screen_permission_revoked_by_the_track_stops_cleanly`, `prm1_screen_permission_revoked_seen_by_the_poll_stops_cleanly`, `prm1_microphone_revoked_keeps_recording_and_warns`, `prm1_camera_revoked_by_the_track_keeps_recording_and_warns`, `prm1_cursor_permissions_do_not_stop_a_recording`, the capture test `prm1_revoked_screen_permission_halts_typed_and_keeps_a_clean_file`, the camera recorder test `camera_access_revoked_mid_recording_flushes_and_reports_a_typed_event` and the app test `prm1_revoked_permission_toast_offers_permissions`, all with fake sources; the real OS behaviour is checked by hand, `tests/manual/PRM-1.md` (section "Revoked during a recording")) Given a recording runs and Screen Recording access is removed, then every track still running is finalized (the last fragment is flushed), `recording.lock` is removed, the recording is kept in the library with the length up to that moment, the pause gaps and the session clock are unchanged, `recording.warning { code: "permission_revoked", permission: "screen" }` and `recording.stopped { reason: "permission_revoked", permission: "screen", message }` are published, and the app shows the toast "Recording stopped: Screen Recording permission was removed" with an "Open Permissions…" button; given only Camera or Microphone is removed, the recording continues, one `recording.warning { code: "permission_revoked", permission: "camera" | "microphone" }` is raised and the track keeps what it wrote.
