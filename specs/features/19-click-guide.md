# Click Guide (GDE)

**0.3.4, maintainer plan of Nov 14, 2026** (`specs/plans/release-0.3.4-plan.md`). One task clicked through once becomes a numbered guide with a screenshot of each click. UI name: **Click Guide**. IDs GDE-1 to GDE-4; guides are a new capture kind (`guide`, folder extension `cmguide`), see below.

**Rules that apply to the whole file**
- **Privacy.** It listens to global clicks, which needs Input Monitoring on macOS (CaptureMann already asks for it for the cursor track, REC-7) and the equivalent hook on Windows and X11. It **never records keystrokes**. It shows a HUD with the step count, Pause and Stop, excluded from the shots (REC-6). In 0.3.4 Click Guide records clicks only and does **not** mark or blur text: nothing flags a step that shows an email, a token or a name, and the draft step title is built from the text near the click, so it can hold such text too (the user checks the titles and the pictures before sharing). **Edit image** on a step opens the screenshot editor, where Blur (B), Pixelate (X) and Auto-redact work on that step's picture. Marking steps with redaction proposals is withdrawn (GDE-1.AC4) and comes back in a later release. A click inside the CaptureMann HUD is not a step.
- **When the frame is taken.** Many UIs change on mouse-up, so the frame is taken on **mouse-down** and the click point is kept: the step shows what the user clicked, not the result. Spike S3 measures the latency on each system; if frames arrive late, the capture keeps a rolling buffer of the last 100 ms of the target.
- **Storage.** A guide is a capture of the new kind `guide` in a folder `<name>.cmguide`: `manifest.json` (kind `guide`), `guide.json` and one screenshot bundle per step. A 0.3.3 app does not index a folder with an unknown extension, so it neither lists nor damages guides. The library index, search, delete, move and rename treat a guide like a recording-sized bundle; tests cover each.
- **`guide.json` (frozen, schema 1; shape confirmed by the maintainer Nov 14, 2026).** `{ "schema": 1, "title", "intro", "numbering": "number" | "upper" | "lower", "target": { display_id | window_id | display_id + rect }, "step_seq", "steps": [ { "id": "step_<n>", "type": "image" | "note", "title", "note", "image": "<folder under steps/>", "click": { "x", "y", "button": "left" | "right" | "middle", "count", "scale" (optional, display scale factor, absent means 1) }, "focus_crop": bool, "has_proposals": bool (kept for schema 1; always false since 0.3.4, and an old file that says true still reads; the tools do not return it) } ], "undo": [ { "name", "state": { "title", "intro", "numbering", "steps" } } ], "redo": [ ... ] }`. `click` is in physical px of the step's `original.png`. A note step has no `image` and no `click`. Unknown fields are kept; a higher `schema` is refused. The folder layout is `manifest.json`, `guide.json`, `steps/<name>.cmshot/` (one ordinary screenshot bundle per image step) and `.undo/` (the image folders of deleted steps while the undo history can still bring them back; removed for good once no history entry needs them, so `steps/` never holds an orphan, GDE-2.AC2). A step picture is addressed as the capture id `<guide_id>/<step_id>`. The library index is schema 4 (`kind` may be `guide`); a 0.3.3 app finds schema 4, rebuilds its own index from the folders and never lists the `.cmguide` folders.
- **Wayland.** Global clicks may not be available; when the portal gives no input events, Click Guide is shown disabled with the reason (spike S6).

### GDE-1 Click Guide: record
**Priority** P1 · **Status** Ready (0.3.4; GDE-1.AC4, the redaction-proposals marker, withdrawn Nov 15, 2026) · **Crates** cm-capture, cm-daemon, cm-library, apps/desktop · **Depends on** CAP-1, REC-6, REC-7 (click listening), ANN-5, ANN-6, PRM-1

**User story.** As a support engineer or trainer, I want to click through a task once and get a numbered guide with a screenshot of each click, so that I don't capture and number 15 screenshots by hand.

**Description**
- **Start:** **New Click Guide** from the capture overlay, the tray, the launcher, the library and a tile in the sidebar's capture dock (second row, beside Long Shot; design S14, Nov 15, 2026: disabled with the reason while a Long Shot or a recording runs, and on a desktop that gives no click events; active while the bar is open, a click brings it to front). The user picks a display or a window to follow, then presses Start (a 3-second countdown, as in REC-4). **New Click Guide** follows the display under the pointer; **Click Guide of a window…** (library header, application menu) opens the window picker of the window screenshot with a **Start guide** button and follows the chosen window, so only clicks inside it are steps. No region picker (maintainer decision, Nov 15, 2026).
- **Each mouse-down** inside the target becomes a step:
  - CaptureMann takes a frame of the target (the frame is taken on mouse-down) and records the click point and the button.
  - It adds a hollow highlight ring centred on the click point and a numbered step badge on the ring's upper-left, as normal ops, so the user can edit them. (Changed Nov 14, 2026 after the first real guide: a badge on the click hid the label.)
  - It writes a draft step title from the text recognized nearest the click, for example `Click "Save"`. Text counts as near within 80 logical px of the click (160 physical px on a 2x display). With no text near the click, the title is `Click here`.
  - Double-clicks and right-clicks are noted in the title (`Double-click`, `Right-click`).
- **Step crop:** each step can show the whole target or the **guide crop** (maintainer review of a real guide, Nov 15, 2026: a crop centred on each click made the framing jump between steps). The guide crop is ONE rectangle for the whole guide: the bounding box of the click points of all image steps, padded by half the default focus size (600 × 400 logical px times the click's display scale) on every side, so it is never smaller than the default 1200 × 800 logical px (2400 × 1600 physical px on a 2x display), and moved, not shrunk, to lie inside the frame; when it covers more than 85 % of the frame there is no crop at all. Steps whose frames differ in size (the display changed during the guide) form one group per frame size, each with its own rectangle. `focus_crop` stays the per-step switch; every step with it on stores the guide crop as its own `crop` op (physical px), recomputed whenever a step is added, deleted, retaken, undone or redone, so adding a click far from the others widens the crop of the earlier steps too; a guide is not rewritten when it is merely opened. Both views are stored: the frame is the image, and the crop is a non-destructive `crop` op (ANN-1); the ring and badge are in original-frame coordinates and do not move.
- **HUD:** step count, Pause, Add note step (a step with no image, for "Type your password"), Undo last step, and Stop. The HUD is excluded from the shots.
- **The bar** (design S17, Nov 15, 2026): 58 px high, as wide as its content and never wider than 720 px or the display less 48 px; the rectangle given to the daemon for AC2 is the bar's real width (the text is measured, not a constant). States: **countdown** ("Starting… 3", "Stop or Esc cancels"; Stop and Esc cancel, Pause, Note step and Undo step are disabled until the guide listens), **recording**, **paused** (the dot turns grey, Pause becomes Resume, the second line starts "Paused ·") and **window closed** (below). When the bar would pass its limit the labels turn into 44 px icon buttons in this order: Undo step, Note step, Pause or Resume; then the second line hides. Stop, the dot and "Step n" never collapse; a collapsed button keeps its label as tooltip and accessible name; a label is never cut with an ellipsis and never wraps. The second line shows at most 40 characters and then an ellipsis.
- **Following a window** (design S16): the window picker in this purpose says "Follow a window. Only clicks inside this window become steps. Clicks anywhere else are ignored." and its button is **Start guide** with the line "3-second countdown after Start guide"; the bar's second line reads `Following "{window}" · clicks only` (the name cut at 28 characters with an ellipsis, the full title as tooltip, no extra chip). In the library header the secondary **Click Guide of a window…** comes first and the primary **New Click Guide** last; when the header has no room for both the secondary is an icon button (app-window) with its label as tooltip; the empty state shows the same pair centred.
- **The 500-step cap and the queue** (QA macOS pass 6, CG-9, CG-10): a guide holds at most 500 steps. At the 450th the daemon publishes `guide.near_limit { guide_id, step_count, remaining: 50, max }` and the app shows the toast "50 steps left. Stop and start a new guide to keep going." At the 500th it publishes `guide.limit_reached { guide_id, step_count, max }`, stops listening and **stops the guide itself** as `stop_guide` does (saved, every step kept, `guide.stopped` follows, the bar closes); the app shows "The guide reached 500 steps and was saved. Start a new guide to keep going." with **Open**. Steps still in the queue at that moment are dropped. Any `guide.error` also shows the toast "A click was not saved: {reason}", at most once in 10 s. The bar closes for `guide.stopped` of its own guide, whoever stopped it. The click filter never holds more than 8 pictures waiting for the worker (a whole-display picture is 6 to 25 MB): a click while 8 wait is not saved and publishes `guide.error { code: "busy" }` instead of the queue growing; the guide editor drops its decoded pictures when it is left. Tests: `cg_9_*`, `cg_10_*` in `crates/cm-daemon/tests/guide.rs` and `cap_tests` in `apps/desktop/src/ui/guide_view/hud.rs`.
- **The followed window closes** (design S16): the daemon looks for the window every 500 ms and, when two looks in a row do not find it, pauses the guide itself and reports it: `get_guide` answers `state: "paused"` with `window_closed: true` and the event `guide.window_closed { guide_id, window_id, step_count }` (with `guide.paused`) is published. Resuming (`set_guide { paused: false }`) answers `invalid_input` while the window is closed; the steps already taken are kept and `stop_guide` saves the guide as for any stop. The bar swaps Pause, Note step and Undo step for "Window closed" and "Pick a window…", the dot turns amber, and a toast says "{window} closed. The Click Guide is paused. Your N steps are kept." with **Pick another window** and **Stop and open guide**. "Pick a window…" and "Pick another window" stop the guide (kept) and open the window picker for a new guide.
- **Privacy** (privacy rules below): no keystrokes; no text is marked or blurred (Auto-redact marking withdrawn for 0.3.4).
- **Result:** a capture of the new kind `guide`. Its folder holds `guide.json` (the title, intro, and the ordered steps with title, note, image id and click point) and one screenshot per step. Each step image is a full screenshot capture inside the guide, so every editor tool works on it.

**Acceptance criteria**
- **AC1** A scripted run that clicks 5 buttons in a test app produces a guide with 5 steps in order. Each step image shows the button's state before the click, its ring is centred on the click point within 2 px (the ring is hollow, so the clicked label stays visible) with the numbered badge on the ring's upper-left, and its title names the button text.
- **AC2** Clicks on the HUD, or outside the target, add no step.
- **AC3** Pause, 3 clicks, Resume. No steps are added while paused.
- **AC4** *Withdrawn for 0.3.4 (maintainer decision Nov 15, 2026; moved to a later release)*. (Was: one step shows an email address; that step is marked "Has redaction proposals", and nothing is blurred until the user accepts.)
- **AC5** macOS without Input Monitoring. Starting shows the permission card and its button; nothing records.
- **AC6** Wayland. Global clicks may not be available. If the portal gives no input events, Click Guide is shown disabled with the reason, and the rest of the app is unaffected.
- **AC7** (design S16) A guide that follows a window whose window closes: within about 1.5 s `get_guide` says `state: paused, window_closed: true`, a click now adds no step, `set_guide { paused: false }` is refused, and `stop_guide` returns the guide with the steps taken before (daemon test `gde_1_a_closed_window_pauses_the_guide_and_keeps_its_steps`).
- **AC8** (design S17) The bar is 58 px high and at most min(720, display less 48) px wide in English, Vietnamese and the pseudo-locale, and with every text 40 % longer; labels collapse in the order Undo step, Note step, Pause or Resume, then the second line hides; the exclusion rectangle is the bar's measured width (`apps/desktop` tests `s17_*`, `ui::bar_layout`).

### GDE-2 Click Guide: edit
- **Guide editor:** a list of steps on the left (drag to reorder, delete, duplicate, insert a note step, retake a step's image) and the selected step on the right, with its title and note fields and its image. **Edit image** opens the normal annotation editor for that step and comes back to the guide.
- The guide title and an intro paragraph sit at the top. Step numbers follow the order, with the numbering style of ANN-6 (`1 2 3`, `A B C`).
- Every change is one undo step, through the same history as ANN-3.
- **The step picture** (design S19, Nov 15, 2026): contain, never cropped and never upscaled past 100 % (a screenshot's own pixels over the display's scale). Its maximum height is the right column's height less the title row (40), the note (40), the action row (32), the meta line (16) and the four 12 px gaps, about 524 px in a 900 px window; below 240 px the column scrolls instead. When the fitted width is under 60 % of the column the picture is centred on #0D0D0F with the chip "Tall picture · click to see full size". A click or Space opens a full-size viewer over the editor (actual size, scrolls inside, Esc or the close button closes it); the badge and the ring are part of the rendered picture, so they scale with it. `ui::guide_view::fit` holds the arithmetic and its tests.
- **AC1** Moving step 4 to position 2 renumbers the badges and titles in one undo step, and undo restores the old order.
- **AC2** Deleting a step leaves no orphan image in the guide folder after the next save. `steps/` never holds an image of a deleted step; the image folder waits in `.undo/` while the guide's undo history can still restore it, and `.undo/` is emptied once no history entry references it (maintainer, Nov 14, 2026).

**Built Nov 14, 2026 (Track D, tested with fakes, no real click or screen):** the guide bundle and its history (`cm-library::guide`), the click listener (`cm-cursor::clicks`, mouse-down only), the session and the five tools (`cm-daemon::guide`), Markdown, HTML and rich-text export, `capturemann guide ...`, the guide editor page, the Click Guide bar and the plugin skill `write-a-how-to`. PDF is built too (spike S4 passed, `docs/project/spikes.md`: `krilla`, Geist fonts embedded, one or two steps per page, A4 or Letter). Not built: drag to reorder (the editor has Move up and Move down), the Input Monitoring card of S3 (a toast says what is missing), the step toast and the click ring on screen, and entry points other than the app menu.

**Built Nov 14, 2026 (Track D2, tested with fakes and the pure models; nothing seen on screen on the Mac):** drag to reorder in the guide editor (Move up and Move down stay as the keyboard way; one `set_guide`, one undo step); Edit image opens the annotation editor on the step and its breadcrumb returns to the guide, which reads itself again; the Input Monitoring card of S3 (GDE-1.AC5) before anything is shown or recorded; the Wayland disabled state with the reason (GDE-1.AC6: the launcher row and the library button are dimmed with the reason, the tray item answers with a toast); entry points in the tray, the launcher and the library header; the sidebar item Click Guides with a count, the Click Guides chip and the empty state; the bar's exclusion rectangle in physical px on Windows (it was given in points, so on a 125 % or 150 % display the part of the bar outside the points rectangle could make a step); `tests/manual/GDE.md`, the cm-regress cases `guide.edit_export`, `guide.refusals` and `guide.real_clicks`, and the real-recognizer check of GDE-3.AC2 for Markdown, HTML and PDF (`crates/cm-daemon/tests/guide_ocr_real.rs`, ignored). Still not built: the 52 px click ring and the step toast on screen (they need a capture-excluded layer window per click), a keyboard shortcut for New Click Guide, and the exclusion rectangle on Linux X11 with a scaled display.

### GDE-3 Click Guide: export
- **Markdown:** a folder with `guide.md` and an `images/` folder of PNGs (rendered, so annotations and redactions are applied). The links are relative, so it pastes into a GitHub wiki or a docs repo as is.
- **HTML:** one self-contained file with the images embedded, light and dark styles, a table of contents and print styles.
- **PDF** (*if spike S4 passes*): A4 or Letter, one or two steps per page. If the spike fails, PDF moves to 0.3.5 and HTML's print styles are the fallback.
- **Copy as rich text:** pastes into a ticket, Notion or Google Docs.
- **Options** (design of Nov 14, 2026, board S9): where to save; step headings as `1. Title`, `Step 1 · Title` or `Title only`; image size 1× or 2× (2× writes the images at twice the guide's reading size, never larger than the frame); switches for the intro, the step notes, and note steps that have no image. The export runs directly: the sheet has no redaction warning in 0.3.4.
- DOCX and PPTX are out of scope (section 7).
- **AC1** The Markdown export of a 5-step guide renders on GitHub with 5 images, in order, with titles. No absolute paths.
- **AC2** In any export, a step image with a blur shows the blur. OCR finds no text inside the blurred rectangle.

### GDE-4 Click Guide: agent interface
- **New tools:**
  - `start_guide { target }` (**Confirm**, because it listens to clicks).
  - `stop_guide`.
  - `get_guide { guide_id }`.
  - `set_guide { guide_id, steps }` (reorder, titles, notes, delete; one revision).
  - `export_guide { guide_id, format: "markdown" | "html" | "pdf", dest }`.
- The CLI has the same commands as `capturemann guide ...`.
- A plugin skill, `write-a-how-to`, shows the flow: start, the user clicks, stop, the agent rewrites the titles from the step text, then exports.
