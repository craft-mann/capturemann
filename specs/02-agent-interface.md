# Agent interface

## Principles and permission model

Agents get the same actions as the GUI through one action bus; publishing and deleting always pause for a human confirmation on screen, because they publish publicly or destroy data, and so does starting a recording unless the user turned that off for AI agents; the user can also make any tool that changes something ask first ("Two controls, one model").

| Tier | Actions | Behavior |
| --- | --- | --- |
| **Free** | List, read, capture screenshot, annotate, trim, layout, export, transcribe, generate metadata, upload to a connected drive | Runs immediately; logged as a revision by `agent:<client name>`; undoable |
| **Confirm** | Start recording (the user can set it to Allow for AI agents, OD-24), publish to any platform, delete a capture or a remote upload, change the folder the library lives in (`move_library`), discard or restart a recording take (internal actions, below) | Native dialog shows exactly what will happen (target, privacy, title, account); the tool call waits up to 5 min, then returns `user_declined` or `confirmation_timeout` |
| **Never** | Read or export OAuth tokens or API keys; change privacy settings of existing remote posts; disable the recording indicator | Not exposed at all |

**Rules**

- **Least surprise.** A recording started by an agent shows the same border, timer and stop button as a manual one.
- **One call, one undo step.** Each tool call is one action and one batch of commands.
- **Idempotency.** Mutating tools accept an optional `request_id`; a repeated id returns the first result instead of acting twice (important for upload and publish).
- **Long work is a job.** Tools that take more than a few seconds return a `job_id` at once; clients follow progress with `get_job` or the event stream.
- **Typed and versioned.** Every tool has a JSON Schema for input and output; breaking changes bump the tool name (`publish_video_v2`).
- **Per-client allow-list.** Settings → Agents & CLI lists connected MCP clients; each can be limited to read-only or blocked. **The policy is keyed by the name a client declares in `session.hello`, so it is not a security boundary against a malicious local process** (which can declare any name): it limits well-behaved agents and tells the user who asked. A connection's name is immutable after its first `session.hello`, and `session.hello`, `events.subscribe` and `actions.list` obey the policy too (a Blocked client gets `client_blocked`). The Confirm gate, the app-only settings and the resource limits do not depend on names. Failing closed is built: when the desktop cannot restore the policy list, clients with no entry are refused with `data.reason: "default_deny"` until the user reviews the list (setting `agents.deny_unknown_clients`, Settings → Agents & CLI); on a normal install a client with no entry is allowed.
- **Two controls, one model (decision OD-24, Oct 25, 2026; supersedes OD-2).** Settings → Agents & CLI shows a per-tool control with the labels **Allow** and **Ask first**. They are labels over the two tiers, not new tiers: **Allow** = an agent's call runs as **Free** (no dialog); **Ask first** = it pauses on an on-screen confirmation like a **Confirm** tier call. The user can change them in two directions only, and they are stored in one app-only setting, `agents.tool_policy`:
  - **Tighten.** Every Free tool that changes something (`mutating` in `ACTIONS`: `capture_screenshot`, `annotate`, `set_settings`, `export_video`, `upload`, `stop_recording`, the edit tools, ...) can be set to **Ask first**. Default **Allow**.
  - **Loosen exactly one tool.** `start_recording` can be set to **Allow**: an AI agent then starts a recording with no dialog (the recording border, timer and Stop button, the tray indicator and the agent toast "Started by <agent>" with its Stop button still appear, and the activity log says `approval: "policy"`). Default **Ask first**. Turning it on asks once in the app ("Let AI agents start recordings without asking?").
  - **Locked.** Read-only Free tools (`list_*`, `get_*`, status reads, suggestions) stay **Allow**: an ask-first on a polling read would be unusable. `publish_video`, `delete_capture`, `run_fps_selftest`, `download_model`, `remove_model`, `download_text_model`, `remove_text_model`, `move_library` and every other Confirm-tier or Never-tier operation stay **Ask first** or unavailable, so NFR-11 keeps its guarantee for publishing and deleting. Internal first-party actions are not tools and have no setting.
  - **Who is asked.** Only agent calls (socket clients over MCP, the CLI or JSON-RPC). The GUI user (`Actor::User`) is never asked. Per-client policy (Allowed / Read-only / Blocked) is separate and stricter-wins: it refuses first, before any dialog, and a Read-only client is refused `start_recording` even when it is set to Allow.
  - **Setting.** `agents.tool_policy` is a JSON object `{ "<tool>": "allow" | "ask" }` that lists only the tools whose value differs from the default. `agents.*` is app-only for agents, so an agent can neither change nor widen it. A write is refused with `invalid_input` when the shape is wrong, the tool is unknown or internal, a value is given for a locked tool, or anything but `start_recording` is loosened; a stored value is **read with the same rules and every entry they refuse is ignored** (treated as the default), so a hand-edited settings file can never loosen publish or delete.
  - **Effective tier.** The daemon computes `effective_tier(tool, actor)` on every call from the live settings (no restart; a change applies to the next call, a dialog already open is not affected): Free becomes Confirm for a tightened tool, and Confirm becomes Free for `start_recording` set to Allow. `actions.list` returns it as the additive field `effective_tier` next to `tier`, and the MCP tool descriptions and server instructions say that a mutating tool may be set to Ask first.
  - **The dialog of a tightened tool is generic**, built in the app from `kind: "tool_ask_first"` and `params: { tool, title, client, lines: [{ key, value }], omitted }`: the agent chip, the sentence "<agent> is asking to run "<tool title>"", and at most 8 key/value lines of the call's parameters. Long values are cut at 120 characters, paths are shown as given, nested values are shown as `{...}` or `[3 items]`, and a key that looks like a secret (`token`, `secret`, `password`, `api_key`, `credential`, `bearer`, `authorization`, `cookie`) is never shown. It has the same 5 minute timeout, queue and idempotency by `request_id` as every confirmation. Cancel returns `user_declined` with `data.reason: "ask_first"` (exit code 3); no answer returns `confirmation_timeout`.
  - The kit's capability rows group real tools: Take screenshots = `capture_screenshot`; Start & stop recording = `start_recording` / `stop_recording`; Save to cloud drives = `upload`; Publish to social = `publish_video`. The page lists every tool by its own name, with a "Changed" marker on a row that differs from its default and a "Reset to defaults" button.
- **Tool names.** Names shown in the kit (`capture.screenshot`, `capture.region`, `record.start`, `save.cloud`, `publish.*`) are illustrative. The real names are the ones in this document (`capture_screenshot`, `start_recording`, `upload`, `publish_video`); the UI shows these in mono.

| `recording.discarded` | a take was deleted, the countdown was cancelled, or the start failed | `capture_id` (null before the session existed), `reason`, and `error { code, message }` when `reason` is `start_failed` |
| `recording.recovered` | at launch, per crashed recording that was repaired | `capture_id`, `lost_ms` (upper bound, one fragment), `title`, `duration_s`, `missing_tracks` (no `recording_id`: it is not a run of this process) |

`reason` in `stopped` and `discarded` says who or what ended the run: `user` (a stop call), `max_duration`, `disk_full`, `system_sleep` (an audio recording: the computer went to sleep, VOC-1; the take is kept), `screen_halted` (window closed or display gone), `screen_encoder_failed`, `permission_revoked` (the OS removed Screen Recording access mid-recording: the run stops cleanly, the take is kept, and `stopped` also carries `permission: "screen"` and a `message`), `shutdown` (app quit), `engine_failed`, `no_frames` (stopped before the first frame), `engine_dropped` (the capture session was dropped by the OS), `error`; for discards also `restart`, `countdown_cancelled`, `starter_gone` and `start_failed`. The self-test events (`recording.selftest`) carry the same `indicator` as a recording on `started`. `capture.created` follows `recording.stopped` and `recording.recovered`.

**`recording_id` and `capture_id`.** `recording_id` names one *run* of the recorder and exists as soon as a start is accepted, including during the countdown; a cancelled or discarded run has a `recording_id` and no capture. `capture_id` is the library id of the bundle, created when `recording.started` fires, and is what every capture tool (`get_capture`, `trim`, `export_video`, ...) takes. The pause, resume, stop and status tools take the `recording_id` (or none, meaning the running one).

## CLI and JSON-RPC

The CLI is a thin client of the running daemon (it starts one if none is running); every command takes `--json` for machine-readable output, and the JSON-RPC methods use the same names as the MCP tools.

```bash
# discovery and settings
capturemann targets --json
capturemann devices
capturemann settings set recording.size source recording.fps 60 recording.codec hevc

# screenshot
capturemann capture screenshot --window "Visual Studio Code" --annotate ops.json --out step1.png

# record a 4K60 lesson with a circle webcam bubble bottom-right (asks for confirmation)
capturemann record start --display 1 --size source --fps 60 \
  --camera on --camera-shape circle --camera-pos bottom-right --mic default --system-audio
capturemann record pause        # also: resume, stop, status; each takes --id <recording_id>
capturemann record start --audio --preset online --countdown 0   # audio only (VOC-1): --mic <id>, --system-audio, --preset room|online|lecture|product|note, --people N (1 to 8)
capturemann record marker --label "Decision"   # or: --capture <id> --at <seconds> for a finished recording
capturemann record status --json
capturemann record watch        # streams recording.* events (--topic, --max-events)
capturemann record stop

# AI and editing
capturemann ai transcribe rec_01JA8K2M7Q
capturemann ai suggest-cuts rec_01JA8K2M7Q --apply
capturemann ai metadata rec_01JA8K2M7Q --platform youtube --json > meta.json

# export, store, publish
capturemann export rec_01JA8K2M7Q --preset youtube-4k
capturemann export rec_01JA8K2M7Q --preset vertical-1080
capturemann export rec_01JA8K2M7Q --wait            # built: the interim `quick` preset, waits for the file
capturemann upload rec_01JA8K2M7Q --to gdrive:/Lessons --copy-link
capturemann library move /Volumes/Big/CaptureMann --wait   # asks on screen; copies, verifies, then switches (restart to use it)
capturemann publish rec_01JA8K2M7Q --to youtube --meta meta.json --privacy unlisted
capturemann jobs watch

# MCP server for agents
capturemann mcp            # runs `cm-mcp` (stdio; `--http` for local HTTP with a bearer token)
capturemann mcp --http     # local HTTP on 127.0.0.1, token-protected
```

Build note (Oct 25, 2026): the MCP server is the separate `cm-mcp` binary (stdio, or `--http`), and `capturemann mcp [--http]` launches it (run against a scripted client, see `verification/REGRESSION-2026-10-25-claude.md`). `publish_video` without `account_id` publishes to the platform's default account (the only one, or the one marked Default in Settings → Destinations; maintainer decision Oct 25, 2026), and the confirmation dialog names it. The CLI covers recording (`record start|pause|resume|stop|status|watch`), `devices`, `export` (presets and GIF/WebM), `ai`, `upload` and `publish`.

**JSON-RPC transport**: Unix socket on macOS (`~/Library/Application Support/CaptureMann/daemon.sock`, 0600 in a 0700 directory), named pipe on Windows (`\\.\pipe\capturemann`, not built); JSON-RPC 2.0, one request per line. Besides the tool names the daemon answers `session.hello { client }` (declares the client name, immutable per connection), `events.subscribe { topics? }`, `actions.list` (`[{ name, tier, effective_tier, mutating, available, internal }]`; `effective_tier` is the tier a call from that client gets now, after the user's per-tool permissions) and `rpc.cancel { id }` (cancels one in-flight request of the same connection; MCP forwards `notifications/cancelled` through it so a waiting confirmation dialog closes). Requests without an `id` are notifications; `id: null` is accepted but discouraged; an `id` that is not a string, number or null, and any batch (array), is refused with `-32600`. Limits per connection: 64 requests in flight (more get `busy`), 16 MiB per line, 32 MiB of unread output; per daemon: 64 connections, 3 pending confirmations per client and 16 in total, an activity log of 2,000 entries and an idempotency cache of 512 entries and 64 MB (images are dropped from cached results above 64 KiB, so a replay of a very large result omits the image).

```json
{"jsonrpc":"2.0","id":7,"method":"publish_video",
 "params":{"capture_id":"rec_01JA8K2M7Q","platform":"youtube","account":"UCx…",
           "metadata":{"title":"Kubernetes probes in 5 minutes","privacy":"unlisted"},
           "request_id":"pub-2026-10-19-001"}}
```

**Exit codes**: 0 success, 1 internal error or not implemented, 2 bad input or not found, 3 user declined a confirmation or it timed out, 4 permission missing (screen, camera, mic), 5 platform, network, disk or daemon-unreachable error (`daemon_unavailable`, also for `capturemann daemon status`), 6 job failed or busy. The authoritative table is in `specs/README.md`.
