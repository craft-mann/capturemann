# CLI and MCP reference

Reference pages for the command line (`capturemann`) and the MCP server (`cm-mcp`), written so the product website can be updated from them.

| File | What it is |
| --- | --- |
| [cli.md](cli.md) | Every command and subcommand of `capturemann` (105, in `--help` order): synopsis, flags with values, allowed values and defaults, confirmation behaviour, the matching MCP tool, examples, exit codes, environment variables, how the CLI finds the daemon. |
| [mcp.md](mcp.md) | The MCP server: starting it, client config, permission tiers and the per-tool policy, idempotency, errors, events, resources and prompts, then all 89 tools with an input table, return fields, errors, CLI equivalent and an example call. |
| [tools.json](tools.json) | The same tool facts for machines: per tool `name`, `area`, `areaTitle`, `tier` (`free` or `confirm`), `policy`, `readOnly`, `destructive`, `acceptsRequestId`, `confirmWhen`, `preview`, `previewParams`, `spec`, `cli`, `description` (as the server emits it), `inputSchema` and `outputSchema` (as emitted). |

Wording rule of the repository: nothing here is "verified" without a report in `verification/`. These pages were produced from the built binaries and the source of the 0.3.4 build (worktree at commit 13cfa99a), and the examples were run on one Mac against a throw-away library. No report was stored for them.

## Where each fact comes from

- **Tools** (names, descriptions, schemas, read-only and destructive hints, the `_meta.stage` of Preview tools): `tools/list` over stdio from the built `cm-mcp`. The count (89) is what the server answers, and `crates/cm-mcp/tests/stdio.rs` asserts it.
- **Tier and policy** (`tier`, `policy`): the tier sentence in each tool description and `crates/cm-daemon/src/tool_policy.rs` (`locked_allow`: read-only; `default_allow`: Free and changes something, the user can set Ask first; `default_ask`: `start_recording`; `locked_ask`: every other Confirm tool).
- **Commands**: `capturemann --help` and `--help` of every subcommand, recursively. The tool-to-command map is the `CLI_COMMANDS` table in `crates/cm-cli/src/lib.rs`.
- **Examples with output**: run with the built `capturemann` against a headless `cm-daemon` whose library, config folder and socket were in a throw-away folder (`CAPTUREMANN_LIBRARY`, `CAPTUREMANN_CONFIG_DIR`, `CAPTUREMANN_SOCKET`, `CAPTUREMANN_SECRETS=file`). One generated 640x400 PNG was imported with `capturemann import`. Nothing was captured or recorded, no model was downloaded, no account was connected, and no real library or running app was touched.
- **Client config snippet**: `apps/desktop/src/ui/settings/model.rs` (`client_config`) and `apps/desktop/src/launcher/mcp_config.rs`.
- **Install locations**: `packaging/macos/bundle.sh`, `packaging/windows/installer.nsi` and `README.md`, `packaging/linux/build-deb.sh`, `packaging/linux/install.sh` and the repository `README.md`.

## Regenerate

From the repository root. The build needs no speaker engine, models or network (`--no-default-features` skips the speaker engine; the tool list does not depend on it).

```sh
CARGO_TARGET_DIR=/tmp/cm-refdocs cargo build -p cm-cli -p cm-mcp -p cm-daemon --no-default-features --locked

# rewrite tools.json from the built server
python3 scripts/gen_agent_reference.py \
  --mcp-bin /tmp/cm-refdocs/debug/cm-mcp --cli-bin /tmp/cm-refdocs/debug/capturemann --write

# check that tools.json is current and that cli.md and mcp.md name every tool and every command
python3 scripts/gen_agent_reference.py \
  --mcp-bin /tmp/cm-refdocs/debug/cm-mcp --cli-bin /tmp/cm-refdocs/debug/capturemann --check
```

`--check` fails (exit 1) when `tools.json` differs from what the server answers now, when a tool name is missing from `mcp.md` (as `` `name` ``), when a command is missing from `cli.md` (as `` `capturemann <path>` ``), or when the tool count sentence is out of date. Without `--mcp-bin` and `--cli-bin` the script looks in `$CARGO_TARGET_DIR/debug` or `target/debug`. A new tool must also be added to `AREAS` in the script, or the script stops and names it. The script is not part of CI.

The Markdown pages are not generated by the committed script. Their tables and per-command sections were assembled from `tools.json` and the `--help` text by a one-off script that is not in the repository, and the surrounding prose was written by hand. After a change to a tool or a command, run `--write`, run `--check`, and edit the page by hand where it is out of date; `--check` only guarantees that nothing is missing, not that the text is current.

## Spec differences found

The code is the source of truth here. `specs/02-agent-interface.md` differs from the 0.3.4 build in these places (the spec was not edited):

1. **CLI examples in "CLI and JSON-RPC".**
   - `capturemann ai suggest-cuts REC --apply`: the command is `ai suggest cuts <id>` and only suggests; apply the result with `edit cut`.
   - `capturemann ai metadata REC --platform youtube`: no such command, and no `generate_metadata` tool (the spec table itself says it is later and not built).
   - `capturemann upload REC --to gdrive:/Lessons --copy-link`: `--to` takes a destination id from `capturemann destinations`; the folder is `--folder`; there is no `--copy-link`. There are also `--file` and `--what export|original|both`.
   - `capturemann publish REC --to youtube --meta meta.json --privacy unlisted`: there is no `--to` or `--meta`; the flags are `--platform` (default `youtube`), `--account`, `--title` (required), `--made-for-kids yes|no` (required), `--description`, `--tags`, `--privacy`, `--thumbnail`, `--export-preset`, `--captions`, `--category`, `--playlist`.
2. **JSON-RPC example of `publish_video`.** The spec uses a parameter `account`; the tool takes `account_id` and rejects `account` with `invalid_input` ("account: unknown parameter", run). Title and privacy are flat parameters (a `metadata` object exists too).
3. **`export_image` and `generate_metadata`** are rows of the spec table but are not registered (the spec says so). The internal actions (`freeze_display`, `release_frame`, `long_shot_state`, `window_thumbnail`, `discard_recording`, `restart_recording`, `skip_countdown`) are not tools either, as the spec says. The server registers exactly the other rows: 89 tools.
4. **Resources.** The server also offers `capturemann://capture/{id}/reports`, which the spec resource table does not list; the spec's `capturemann://capture/{id}/cursor` row is not built (the spec says so). The spec table lists the library, a capture, its transcript, jobs and the platform rules.
5. **`get_platform_rules`** accepts `youtube`, `tiktok` and `facebook` in its schema, but only YouTube is built: the others answer `not_implemented` (run for `tiktok`). The CLI `platform-rules` documents `youtube` only.
6. **Windows endpoint.** The spec says the Windows named pipe `\\.\pipe\capturemann` is "not built"; the code defines it as the default Windows endpoint (`crates/cm-ipc/src/endpoint.rs`) and the Windows packages ship the CLI and the MCP server. Not run on Windows here.
7. **"Daemon needed".** It is easy to assume that the CLI needs the app running. In the code the CLI starts a headless `cm-daemon` when nothing listens (unless `--no-start`); only the macOS bundle lacks `cm-daemon`, and the MCP server never starts one. The pages say this.

## Not run, and uncertain

Not run (no safe way against an isolated daemon, or they need hardware, a model, an account or a person at the screen): `targets list` and `capture screenshot` (screen capture), everything under `record` except `record status`, `guide` (all five), `devices`, `export` (needs a recording), `library move`, `upload`, `publish`, `mcp` (stdio blocks; the HTTP start-up lines and the 401 and 200 answers were checked with `cm-mcp --http` directly), `edit` (needs a recording; `edit trim` was run on a screenshot to show the error), `ai` commands that need a model or a recording, and `jobs cancel`, `jobs retry`, `jobs watch`. All tool example calls in `mcp.md` are shapes only except the ones named as run in the error section.

Uncertain:

- The per-tool "Errors" lines come from the codes named in each tool description plus the tier and id rules; they are not an exhaustive list of what a daemon can answer.
- The example calls use illustrative ids and paths (`rec_...`, `gdrive_main`, `/Users/me/...`) and were not validated against a JSON Schema validator; read-only calls with real ids were run for a handful of tools.
- Client config file locations of Claude Desktop, Cursor and other clients are not documented here: only the snippet the app shows is.
- The Linux and Windows install locations are read from the packaging scripts and the README; they were not run on those systems for this page.
