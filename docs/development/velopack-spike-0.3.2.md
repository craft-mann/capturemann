# Velopack spike for 0.3.2: macOS, crate audit, hosting (Nov 11, 2026)

Scope: Phase 0 of the in-app update workstream (`specs/plans/release-0.3.2-plan.md`, section "In-app update with Velopack"), Mac side only. The Windows side is a separate spike on the ThinkPad. Nothing here is product code; the scratch code is `spikes/velopack-mac/` (its own workspace, scripts in `spikes/velopack-mac/scripts/`). Nothing was published, tagged, uploaded or pushed; the maintainer's installed apps, library and settings were not touched. Wording rule: every result below is "run on this Mac (Apple Silicon, macOS 26.6.2, Nov 11, 2026)" unless it says "not verified".

Versions used: `velopack` crate **1.2.161** (MIT, Sep 29, 2026; the newest stable), `vpk` **1.2.161** (`dotnet tool install --tool-path`, .NET SDK 8.0.428 installed user-locally into `/tmp/cm-velo-mac/dotnet`, removed afterwards), `ureq` 3.5.1, `rustls` 0.23.46, `ring` 0.17.14, `zip` 8.6.0.

## Recommendation for macOS: GO WITH CHANGES

Velopack Apply works on macOS as documented: a signed `.app` updates itself in place from a plain static feed, a delta works, a failed hash or a dead feed fails cleanly, and the DMG can stay the first-install format. It is a go only with these changes, none of which is optional: (1) the crate's tree adds one rejected licence (`webpki-roots`, CDLA-Permissive-2.0), one unmaintained crate and one RUSTSEC vulnerability in `zip` 8.6.0, so we need a `deny.toml` decision (an exception for `webpki-roots`, an ignore for `derivative`, and a newer `velopack` or a vendored copy for `zip`); (2) the stock `HttpSource` sends a persistent random `stagingId` and the app id with every check, which contradicts the "no identifier" promise, so we must supply our own `UpdateSource` (the trait is public) that sends a bare GET and verifies a detached minisign signature of every downloaded package before it is accepted (this also gives the integrity check the plan wanted; the stock client verifies only SHA-256 or SHA-1 taken from the same feed); (3) `VelopackApp::build().run()` must be called **only** in `cm-desktop` and with `set_auto_apply_on_startup(false)`, because with the default any process that calls it silently replaces the bundle and relaunches itself; (4) `vpk` adds `UpdateMac` and `sq.version` to the `.app` and so breaks our signature unless it re-signs, and its default re-signing would replace our entitlements, so `make release` needs `--signDisableDeep --signEntitlements packaging/macos/CaptureMann.entitlements` (tested, works); (5) the one check that decides the macOS go, that the Screen Recording, Microphone and Camera grants survive an update, could not be run here and is the maintainer's job (steps at the end). If (5) fails, the answer for macOS becomes NO-GO and the notify-only fallback (D) is the plan.

## Five most important findings

1. **A stock check is not anonymous.** `HttpSource` requests `releases.<channel>.json?localVersion=<v>&id=<app id>&stagingId=<uuid>` with `user-agent: ureq/3.5.1`. The `stagingId` is a random UUID kept in `~/Library/Caches/velopack/<id>/packages/.betaId` (it changed between two of my runs, so it is not a stable machine id, but it is an identifier). Captured on the wire (local server), see A.
2. **`run()` auto-applies.** With a package already downloaded, starting the app with any arguments (I used `version`) replaced the bundle and relaunched through `open -n` with the same arguments; the first process exited 0. Called from `capturemann`, `cm-mcp`, `cm-daemon` or `cm-overlay` this would be a disaster. `UpdateManager::new` returns `Err(NotInstalled)` outside an updatable `.app`, which is how the app learns it was not installed this way (our current 0.3.1 DMG apps have no `UpdateMac`, so they cannot self-update once: the first Velopack build needs a manual DMG install).
3. **The new process can take about 27 to 30 s to start.** Down time between "apply" and the new process running was 0.7 s (4.7 MB scratch app), 1.4 to 1.9 s (190 MB scratch app, warm), but 27.1 s and 29.8 s on the first launch of a never-launched 190 MB ad-hoc-signed bundle (the process sits in `_dyld_start` for that time; cause not diagnosed, probably a first-launch security assessment). Real numbers need a Developer ID build (maintainer step).
4. **Delta is real but the base is missing on first update, and a delta result is not hash-checked.** On the real bundle (0.2.9 to 0.3.1 arm64): full package 88.9 MB (DMG 87.0 MB), delta 22.3 MB (25 %). The first update after a DMG install is always full, because the packages folder starts empty. After a delta the rebuilt full package differs from the feed's full package (92,816,657 vs 90,634,105 bytes in my test) and the client never checks the rebuilt file against the feed hash (read in `manager.rs`: only the delta files are checked). So a detached signature of the full package cannot be used after a delta; the signature check must sit in a custom `UpdateSource::download_release_entry` and cover deltas and fulls.
5. **vpk changes the signed `.app`.** It adds `Contents/MacOS/UpdateMac` (7.7 MB), `Contents/MacOS/sq.version` (symlink) and `Contents/Resources/sq.version`. Without `--signAppIdentity` the bundle no longer verifies ("file added") and the relaunch after an update **hangs** (the process never gets past `_dyld_start`; seen twice). With ad-hoc `--signAppIdentity -` it works; with the default entitlements vpk would give every binary `allow-jit`, `disable-library-validation` etc. and drop our camera and audio-input entitlements; `--signDisableDeep --signEntitlements ours` keeps every helper's own signature and gives `cm-desktop` exactly our two entitlements (tested on a copy of the real 0.3.1 bundle, ad-hoc outer signature).

## A. Crate audit

Run: scratch crate `spikes/velopack-mac` with `velopack = "=1.2.161"`; `deny.toml` copied unchanged from the repo.

**Tree.** `cargo tree -e normal` (macOS arm64): 105 packages, **15 not already in the repo `Cargo.lock`**: `derivative`, `normpath`, `ring`, `rustls`, `rustls-webpki`, `sha1`, `typed-path`, `untrusted`, `utf_types`, `velopack`, `waitpid-any`, `webpki-roots`, `xml`, `zip`, `zopfli`. First clean build of the scratch crate (4 jobs): 2 min 15 s wall, 71 s CPU; incremental link 0.6 s.

**`cargo deny check` (repo rules): advisories FAILED, licenses FAILED** (bans and sources ok). The failures other than the scratch crate having no licence field:
- `webpki-roots` 1.0.12: **CDLA-Permissive-2.0** rejected (the licence the repo kept out on purpose). It is pulled by `ureq`'s default `rustls` feature, which `velopack` enables with default features; we cannot switch it off from outside.
- `derivative` 2.2.0: **RUSTSEC-2024-0388, unmaintained** (proc macro, build time only). Needs one more `ignore` with a reason.
- `zip` 8.6.0: **RUSTSEC-2026-0367, vulnerability** (SUID/SGID bits kept when a privileged process calls `ZipArchive::extract()`; fixed in zip >= 9.0.0). Not reachable in our use (macOS reads only the manifest through `ZipArchive`; `extract_*` is used on Windows for `Update.exe`; neither runs privileged), but `cargo deny` fails on it. The crates.io index also lists `velopack` **1.3.39-g8d2844f** (Oct 17, 2026, a semver pre-release tag) which depends on `zip ^9.0.3`; I did not build or test it, and `vpk`/client versions should match.
- Not a problem: `r-efi` (LGPL-2.1-or-later OR MIT/Apache, Windows UEFI only, passes via the OR), `aho-corasick`/`memchr` (Unlicense OR MIT). `cargo audit` is not installed here; `cargo deny`'s advisory database covers the same data.
- Our existing 7 `unmaintained` ignores show as "not encountered" in this tree, as expected.

**Features.** `default = []`, `file-logging` (log-panics, simplelog, time), `public-utils`. No async, no delta, no TLS feature: the client is synchronous (blocking `ureq`); deltas are applied by the helper `UpdateMac patch ...`, not by the crate; logging is the `log` facade (nothing is written unless the app installs a logger). Sources in the crate: `HttpSource` (with `new_with_options`: headers, timeout), `FileSource`, `GithubSource` (prerelease flag), `GitlabSource`, `GiteaSource`, `VelopackFlowSource` (the vendor's paid hosted service), `AutoSource`, `NoneSource`, plus the public `UpdateSource` trait.

**HTTP and TLS.** `ureq` 3.5.1 with default features: `rustls` 0.23 with the **ring** crypto provider and **webpki-roots** (a bundled Mozilla root list, not the macOS keychain, so a corporate or proxy CA is not trusted), gzip. No `aws-lc`, no `native-tls`. C requirement: `ring` and `cc` compile a little C/asm with the normal toolchain (already needed for whisper.cpp); no cmake or nasm. Our other crates set `TlsProvider::NativeTls` explicitly (`cm-auth/src/http.rs`, `cm-ai/src/model.rs`, `cm-storage/src/http.rs`), so adding `velopack` does not change their TLS; only Velopack's own requests use rustls. Default timeout is **0 = never** (`HttpOptions.TimeoutMilliseconds`), so a custom source or `new_with_options` must set one. HTTPS itself was not exercised (my feed was plain HTTP on 127.0.0.1).

**What one check sends** (source `sources/http.rs`, `download.rs`; captured by `spikes/velopack-mac/scripts/serve.py`, which logs headers):
```
GET /releases.osx-arm64.json?localVersion=0.3.2-spike1&id=dev.capturemann.velospike&stagingId=4c207651-13bd-4d34-b492-ece6acb6a816
    accept-encoding: gzip
    user-agent: ureq/3.5.1
    accept: */*
    host: 127.0.0.1:8099
GET /dev.capturemann.velospike-0.3.2-spike2-osx-arm64-full.nupkg      (same four headers)
```
No cookies, no telemetry call, no other hosts in the crate source (Flow is used only if `VelopackFlowSource` is chosen). A host (or GitHub, or a CDN) sees IP, the app version, the app id and the per-install random `stagingId`. With a custom source none of the query is needed.

**Integrity on a downloaded package** (`manager.rs::verify_package_checksum`, then runs I did): size first, then **SHA-256 if the feed entry has one, otherwise SHA-1** (so SHA-1 is ignored when SHA-256 exists; tested: tampered SHA-1 with correct SHA-256 passed). No signature check by the crate; it relies on the OS code signature after apply. On mismatch it returns `Error::SizeInvalid` or `Error::ChecksumInvalid`, the file stays as `*.partial` (never renamed to `.nupkg`, so never applied; removed by the next download). Tested: truncated file, one flipped byte, wrong feed hashes: all three failed this way. Hash and package come from the same host, so this is integrity against corruption, not against a compromised host.

**Can download and apply be separated?** Yes. `download_updates(&info, progress)` only writes `~/Library/Caches/velopack/<id>/packages/<FileName>` (and, if a base package exists, downloads the delta files and builds the new full package locally); `get_update_pending_restart()` reports it; applying is a separate call (`apply_updates_and_restart[_with_args]`, `wait_exit_then_apply_updates`, `apply_updates_and_exit`) that starts `UpdateMac apply` and waits for our pid. So the app can run its own check between the two. Two catches: (a) after a delta the rebuilt full package is not byte-identical to the feed's full package and is not checked, so a detached `.minisig` of the full package cannot be verified there (finding 4); the check must be in a custom `UpdateSource::download_release_entry` (called before the hash check, for deltas and fulls) or deltas must be switched off (`UpdateOptions.MaximumDeltasBeforeFallback = -1`) and a minisign signature checked on the full package after download; (b) `run()` auto-applies any newer package it finds in that folder, so auto-apply must be off or an unverified file left there would be applied at the next start. Our `minisign.pub` and `sign-linux.sh` pattern fits; the verifier would be the `minisign-verify` crate (0.3.0, MIT, Sep 25, 2026; not built here, not verified).

**Installed by Velopack?** `UpdateManager::new(source, None, None)` (or `VelopackApp::run()`, which logs and returns) locates the app from `current_exe()`: it needs a path containing `.app/`, `Contents/MacOS/UpdateMac` and `sq.version`. Run: the same binary outside an app returned `Err(NotInstalled("Could not locate '.app' in executable path ..."))`; inside the vpk-built app it returned id, version and `portable=true` (on macOS always true). `get_is_portable` is therefore useless as a signal; the `Result` is the signal.

**Channels.** The channel is a string baked into the package (`sq.version`) by `vpk pack --channel`; the feed file is `releases.<channel>.json`. The crate default for macOS is `osx` for any CPU. An arm64 and an Intel build therefore need **different channel names** (I used `osx-arm64`; `osx-x64` for Intel) with separate feeds, else the second pack overwrites the first. `vpk pack --runtime osx-arm64` writes the rid into `sq.version` too.

**`VelopackApp::build().run()`** (source `app.rs`): on macOS it consumes no argument itself (the `--veloapp-install|updated|obsolete|uninstall` hooks exist for Windows and exit the process with 0 when given two arguments; harmless but reserved). Then it builds an `UpdateManager` with `NoneSource`; if the app is not installed it only logs and returns. If a full package newer than the running version is in the packages folder and auto-apply is on (default) and the env var `VELOPACK_RESTART` is not set, it calls `apply_updates_and_restart_with_args(.., original args)` and `exit(0)`. Run: confirmed (above). It also deletes old packages and fires `on_first_run` / `on_restarted` hooks. Consequences: call it first in `cm-desktop::main` only, with `set_auto_apply_on_startup(false)` and our own apply path behind the Confirm-tier action; never in `cm-overlay`, `cm-daemon`, `capturemann`, `cm-mcp` (they run from inside the same `.app` and would also locate it). The relaunch is `open -n <app> --args <restart args>`: **no environment is passed** (my `VELO_LOG` was lost; `CAPTUREMANN_CONFIG_DIR`, `CAPTUREMANN_SOCKET` etc. would be lost for a second instance) and no stdio.

**Size and build time.** Release binary: hello-world 435,008 bytes, with the update code 3,913,744 bytes (+3.5 MB, about 3 % of the 106 MB `cm-desktop`); plus `UpdateMac` 7.7 MB in the bundle (the nupkg compresses it). Build: about 70 s CPU for the 105 packages on a clean tree.

## B. macOS packaging and update behaviour

Tiny scratch app (the spike binary `velo-spike`, ad-hoc signed `.app`, bundle id `dev.capturemann.velospike`, local feed `python3 serve.py` on 127.0.0.1) and, for sizes and signing, copies of the real 0.2.9 and 0.3.1 arm64 apps taken read-only from the DMGs in the main checkout's `target/bundle` (mounted read-only under `/tmp`, copied with `ditto`, **never launched**; packed only under a scratch package id). The maintainer's `CaptureMann-dev.app` was only read (`codesign -d`). Commands (trimmed):

```
vpk pack --packId dev.capturemann.velospike --packVersion 0.3.2-spike1 --packDir pack/app1/VeloSpike.app \
   --mainExe velo-spike --runtime osx-arm64 --channel osx-arm64 --outputDir feed --signAppIdentity -
```

**Files produced** (per version, 4.7 MB app): `<id>-<ver>-osx-arm64-full.nupkg`, `<id>-<ver>-osx-arm64-delta.nupkg` (from the second pack on; it needs the previous full package in `--outputDir`), `<id>-osx-arm64-Portable.zip` (the `.app`, with a `__MACOSX` folder), `<id>-osx-arm64-Setup.pkg`, `releases.osx-arm64.json` (full and delta entries: `PackageId, Version, Type, FileName, SHA1, SHA256, Size, NotesMarkdown, NotesHtml`), `assets.osx-arm64.json`, `RELEASES-osx-arm64` (legacy, SHA-1). A pack of the real 186 MB bundle took 11 to 13 s; the delta 2 s.

**Our `.app` as input.** `--packDir` pointing at an existing `.app` is used as is ("Pre-process" generates nothing). vpk then **adds files into it**: `Contents/MacOS/UpdateMac`, `Contents/MacOS/sq.version` (symlink to `../Resources/sq.version`), `Contents/Resources/sq.version`. Unsigned run: `codesign --verify` says "file added" for those three and the later relaunch hangs (see finding 5). The bundle id stays what `Info.plist` says (when vpk builds the `.app` from a bare folder it invents `com.<id>.<id>`; use `--bundleId`).

**Signing flags.**
- `--signAppIdentity <cert name or ->` re-signs the whole bundle with `--deep` and hardened runtime, using vpk's default entitlements unless `--signEntitlements` is given. Default entitlements are `automation.apple-events`, `cs.allow-dyld-environment-variables`, `cs.allow-jit`, `cs.allow-unsigned-executable-memory`, `cs.disable-library-validation`; under `--deep` they go on every binary. That would drop our `device.camera` and `device.audio-input` and add entitlements `packaging/macos/CaptureMann.entitlements` deliberately leaves out.
- Tested on the real 0.3.1 layout: `--signAppIdentity - --signDisableDeep --signEntitlements packaging/macos/CaptureMann.entitlements`. Result: `codesign --verify --deep --strict` passes; `cm-desktop` has exactly `audio-input` and `camera`; `cm-overlay`, `ffmpeg`, `llama-server` keep their own Developer ID signatures (TeamIdentifier DJ2ALRFN66, identifiers `...overlay`, `...ffmpeg`, `...llama`, no entitlements); only the added `UpdateMac` gets vpk's default entitlements (identifier `UpdateMac-<hash>`, `disable-library-validation` and `apple-events` for the osascript path; it is a small separate binary). With a real identity vpk re-signs the main executable and the bundle with it, same Team ID as the helpers.
- `--notaryProfile <name>` makes vpk zip the app, run `notarytool` and staple. **Not run** (no credentials, no submission). Our `notarize.sh` (API key, Apple ID or `CM_NOTARY_PROFILE`; DMG or zip; staples a DMG) can stay in charge: the flow would be `bundle.sh` (our per-binary signing, hardened) → `vpk pack` with the flags above and **no** `--notaryProfile` → take the `.app` vpk produced (Portable.zip) → `dmg.sh` → `notarize.sh` on the DMG. The `.app` inside the nupkg is then byte-identical to the one inside the notarized DMG, so it carries the same registered ticket; it is not stapled (today's DMG apps are not stapled either: `stapler validate` on the 0.3.1 app says no ticket, `spctl` says "accepted, Notarized Developer ID"). Updated files are written by `UpdateMac`, which does not set the quarantine attribute, so Gatekeeper does not assess them at launch (this is the usual behaviour of such updaters; not separately proven here with a quarantined parent). Needs the maintainer's Developer ID to confirm (below).
- `.pkg` installer: not needed; `--signInstallIdentity` only matters for it.

**DMG as first-install format.** Yes. Made a DMG with the vpk-processed `.app`, mounted it, copied the app to a folder with spaces under another name (`my apps/CaptureMann Spike.app`), ran the update there: it found `sq.version` and `UpdateMac` inside the bundle, updated **in place under the new name**, signature valid afterwards. So the DMG must contain the vpk-processed `.app` (not the one from `bundle.sh`), and `make dmg` should take its input from the vpk output. Existing 0.3.1 installs have no `UpdateMac` and cannot self-update once.

**Where it can update.** Writable folder (my `/tmp` folders; equals `~/Applications`): no prompt. `/Applications` on this Mac is `root:admin 775` and the maintainer's `CaptureMann.app` there is owned by him (`drwxr-xr-x trungtranmba admin`), so for an admin user the replace needs no elevation; I did not write there. When the replace gets "permission denied" `UpdateMac` shows its own dialog ("Administrator Permission Required") and then runs `do shell script "mv -f ..." with administrator privileges` through `osascript` (read from the binary's strings; **not triggered**). Read-only location test (`chmod -R a-w`, `update-silent`): the apply fails with "A permissions error occurred ... will attempt to elevate ... Not allowed to ask for elevated permissions because --silent flag is set"; **the updater still relaunches the app, as the old version**, and the only trace is `~/Library/Logs/velopack_<id>.log`. The app must compare versions after restart and tell the user. A non-admin account was not tested.

**Full cycle** 0.3.2-spike1 to spike2 (and spike3), local feed:
- check 2 to 8 ms; download 7 to 16 ms (local); apply to new process running: **0.66 s** (4.7 MB app). 190 MB scratch app (real 0.2.9/0.3.1 files as payload): 1.7 s, 1.4 s and 1.9 s warm, but **27.1 s and 29.8 s** on two first launches (finding 3).
- Sizes, real bundle 186 MB (0.2.9 to 0.3.1): full nupkg **88,939,418 B**, delta **22,337,705 B** (14 of 32 files patched), `Portable.zip` 88,962,871 B, `Setup.pkg` 88,948,776 B, DMG 87,026,259 B (includes about 33 MB of speaker models, the bundled FFmpeg and `llama-server`). Local delta apply (patch) 3.7 s on this Mac. A 4.7 MB scratch app: full 4.67 MB, delta 4.3 KB.
- First update after a DMG install: full (no base package in the cache). After one update the cache holds the current full package, so the next update is a delta (spike2 to spike3: only the 4,263-byte delta was requested, 216 ms). With the first package seeded into the cache, spike1 to spike3 used two chained deltas (spike2 and spike3 requested, no full).
- **Skipped versions** (spike1 straight to spike3): works; the client picks the latest full package (or chains deltas).
- **Child processes**: an older process from the same `.app` (`velo-spike hold`, with a `sleep` child) kept running through the apply; `UpdateMac` waits only for the pid that called apply and does not stop siblings. The bundle on disk is replaced under them (the case of the Oct 23, 2026 note). So before apply the app must stop its own `cm-overlay` and any helper, and the plan needs a rule for `cm-mcp` processes started by Claude Desktop (they will keep running the old binary until Claude restarts them; the daemon socket protocol must tolerate that skew).
- **Feed unreachable**: `Err(Network(Http(Io(ConnectionRefused))))` immediately; HTTP 404: `Err(Network(Http(StatusCode(404))))`; no default timeout, set one.
- **Truncated, corrupt, wrong hash**: see A (clean errors, `.partial` left, nothing applied).

**Will Screen Recording, Microphone and Camera grants survive?** Not testable here (needs the Developer ID build and the maintainer's TCC database; I did not touch `tccutil`, the Developer ID identity, or the real bundle id). What the code requirement depends on, read with `codesign -d -r-`:
- Real release (0.3.1, Developer ID): `designated => identifier "dev.capturemann.app" and anchor apple generic and certificate 1[field.1.2.840.113635.100.6.2.6] exists and certificate leaf[field.1.2.840.113635.100.6.1.13] exists and certificate leaf[subject.OU] = DJ2ALRFN66`. It names the bundle identifier and the Team ID, not a hash, so any later build with the same bundle id signed with the same Developer ID satisfies the same requirement and macOS keeps the grants (this is the normal Sparkle-style update case). The update must therefore keep `CFBundleIdentifier` `dev.capturemann.app` and the signing identity.
- The maintainer's dev build (`CaptureMann-dev.app`, "CaptureMann Local Dev") has `identifier "dev.capturemann.app.dev" and certificate leaf = H"deb6..."`: also stable across rebuilds; an ad-hoc build has `cdhash H"..."`, which changes every build (grants lost; the known cause of the Oct 23 and Oct 24 notes).
- Risks to check on the real build: vpk re-signing must not change the identifier or the Team ID (tested ad hoc: identifier kept as `dev.capturemann.app`); `UpdateMac` swaps the whole bundle (new inode) and relaunches with `open -n`, which for an old running `cm-desktop` is a new process, so TCC attribution is the app's own bundle id again; the keychain "Always Allow" for the `vault` item (an ACL tied to the code requirement) should also survive for the same reason (plan.md, line 147 says that was never observed on a release update).

**What I could not run on this Mac:** notarization and stapling, a Developer ID re-sign, Gatekeeper on a quarantined first launch, real TCC grants, a non-admin account, `/Applications` and `~/Applications` writes, an Intel build, HTTPS, the cm-desktop with the crate linked, any real recording.

## C. Hosting

**GitHub, `releases/latest`.** GitHub's REST docs (docs.github.com, "Get the latest release"): "The latest release is the most recent non-prerelease, non-draft release, sorted by the `created_at` attribute"; `make_latest` can pick explicitly, never a pre-release. Run (public API and plain GET, no token, Nov 11, 2026): `releases` of `craft-mann/capturemann` lists v0.3.1 (not a pre-release), v0.3.0 (pre), `apt` (pre), v0.2.9, v0.2.8 (pre)...; `GET /releases/latest` returned **v0.3.1**; `https://github.com/craft-mann/capturemann/releases/latest/download/InRelease` redirected (302) to `.../releases/download/v0.3.1/InRelease` even though the `apt` pre-release has an `InRelease` too; `https://github.com/craft-mann/capturemann/releases/download/apt/InRelease` redirected to `release-assets.githubusercontent.com/...` and returned 200 (a tag URL resolves pre-releases and mutable assets). Note the plan's statement "all 0.3.x are pre-releases" is not true any more: v0.3.1 is a normal release today. So `latest/download` works only while the newest non-pre-release carries the feed, and a re-flag of a release would silently change what `latest` means; do not depend on it. Not verified: GitHub rate limits on the redirect host under load (docs do not state a limit for release asset downloads; the API `releases` calls used by `GithubSource` are limited to 60 per hour per IP unauthenticated, which is another reason not to use `GithubSource`).

**Proposed layout: a dedicated release with tag `updates`** (same pattern as `apt`), assets replaced at each release (replace is a delete plus upload; there is a short window where a file is missing: upload new packages first, the feed JSON last):
```
https://github.com/craft-mann/capturemann/releases/download/updates/releases.osx-arm64.json
https://github.com/craft-mann/capturemann/releases/download/updates/releases.osx-x64.json
https://github.com/craft-mann/capturemann/releases/download/updates/releases.win-x64.json      (Windows spike decides)
https://github.com/craft-mann/capturemann/releases/download/updates/<id>-<ver>-osx-arm64-full.nupkg
https://github.com/craft-mann/capturemann/releases/download/updates/<id>-<ver>-osx-arm64-delta.nupkg
https://github.com/craft-mann/capturemann/releases/download/updates/<same>.minisig             (ours)
```
Each request answers 302 to `release-assets.githubusercontent.com`, a signed, short-lived URL (so `HttpSource` joins `<base>/<FileName>` and follows the redirect; `ureq` follows redirects by default; I tested only the redirect with `curl`, not through `ureq`). The feed keeps all deltas for the versions we want to support (the client takes the latest full plus the chain), so the `updates` release grows; prune old deltas and fulls at each release. GitHub release asset limit is 2 GiB per file, fine.
- What GitHub learns: the client IP, `user-agent` (we set it), the path (which channel and version), the time. A custom source sends no query and no identifier.
- Static hosting on `craftmann.app` (the domain currently answers 302; I did not look at how it is hosted): same files at e.g. `https://craftmann.app/updates/osx-arm64/releases.osx-arm64.json`, no redirect, no third-party storage host, stable URLs and full control of headers and logs; costs: bandwidth on a host the maintainer pays for (about 89 MB per full download), publishing step outside `gh release`, and one more host in the privacy text. GitHub is free, already trusted for the DMGs and the APT repo, but adds a second host name (`release-assets.githubusercontent.com`) to the firewall allow list. Either works with `HttpSource`; recommendation: `updates` release on GitHub first (no new infrastructure), keep the base URL a setting so it can move.

## D. Fallback: opt-in notify-only check (sketch, no code merged)

- **URL:** `https://github.com/craft-mann/capturemann/releases/download/updates/latest.json` (one small asset, replaced each release), HTTPS GET, no query, no cookies, `user-agent: CaptureMann` (no version, or the version only if the maintainer wants it), via the existing `ureq` + `NativeTls` agent pattern in `cm-storage/src/http.rs`.
- **JSON:** `{"schema":1,"version":"0.3.2","released":"2026-11-20","notes_url":"https://github.com/craft-mann/capturemann/releases/tag/v0.3.2","min_os":{"macos":"13.0"},"assets":{"macos-arm64":{"url":"...dmg","sha256":"...","size":87026259},"macos-x64":{...},"windows-x64":{...},"linux":{"apt":"sudo apt update && sudo apt install --only-upgrade capturemann"}}}` plus `latest.json.minisig` checked with `packaging/linux/minisign.pub`'s successor key (`minisign-verify`, about 200 lines of dependency-free code) so a hijacked host cannot announce a fake release.
- **Compare:** `semver::Version::parse` (already in `Cargo.lock`, 1.0.28); newer if remote > local and the platform key exists; pre-release channel not offered unless the user opts in.
- **Size of the code:** about 150 to 250 lines in a new small module (fetch, parse, verify, compare, a `check_for_updates` action returning `{current, latest, notes_url, download_url}`), one `updates.*` app-only setting block, one tool and one CLI command (`capturemann update check`), a button and a banner; no new heavy dependencies (`minisign-verify` is the only addition; no `rustls`, `ring`, `webpki-roots`, `zip`, `derivative`, so `deny.toml` stays unchanged). The user downloads the DMG or runs the APT command himself; Homebrew users use `brew upgrade`.
- **What it sends:** the TCP/TLS connection (IP), the request line and `user-agent`; nothing else. The app can show this sentence before the user turns it on.
- **Trade-off against Apply:** no in-place update, no down time, no helper binary in the bundle, no entitlement or signing changes, no child-process question; but the user does the DMG drag and the permission-survival question does not arise (same as today).
