## Decisions and the rule behind the indicator

* **No floating HUD, countdown disc or brackets on Linux** (default, both sessions): the portal records every pixel, so any window of ours over the recorded screen is in `screen.mp4` (REC-5.AC9 says it must not be), and Wayland cannot place or raise a window (no layer-shell on GNOME). The HUD's job is a banner at the top of the Studio window (`recording::surface`, `ui::recording::banner`), the same place toasts already go on Wayland. X11 can opt back in with `CM_LINUX_FLOATING_HUD=1` (HUD and countdown only).
* **The rule** lives in `specs/features/03-recording.md` (REC-5: "The indicator can't be hidden by settings or by agents", AC5), `specs/02-agent-interface.md` (Never tier: "disable the recording indicator", NFR-11) and `specs/platform-acceptance.md` (REC-5, Linux: "the recording indicator stays visible to the user"). What meets it on Linux: (a) the banner, which a recording started from the tray, a hotkey, the CLI or an agent opens the Studio window for (`banner_instead_of_windows`); (b) the tray icon's red state with Stop and Pause in its menu, when a StatusNotifier host exists; (c) the desktop's own screen-share indicator, which GNOME and KDE show for every portal screen share and an app cannot disable (seen in shot 03).
* **What is not possible on Wayland:** a guarantee. A compositor with no screen-share indicator (a bare wlroots session), no tray host and a Studio window the user minimised or put on another workspace leaves a recording with no visible sign; the Studio banner is only seen when that window is. A persistent notification through the portal was not built: the Notification portal cannot show a live timer or a Stop button the compositor would keep on top, and GNOME hides banners after a few seconds. Said plainly here and in `platform-acceptance.md`.
* **Display id:** the recorder now maps whatever display id the caller gave to the one screen the portal dialog picks; the sheet shows no display chips on Linux (the desktop's dialog chooses).
* **Poster and playback:** nothing macOS-only was involved: the poster is FFmpeg (needs a VP9 decoder; the bundled build has it), Play opens the system player, the editor preview decodes with FFmpeg. What changed: the FFmpeg error is no longer followed by "no thumbnail tool on this OS", and Play, Show in folder and links report "nothing is set to open this" (`xdg-open` exit code 3 or 4, read within 1.5 s).

## Not done, found, left alone

* Quality and codec choices for the VP9 recorder in Settings (not my files).
* The Start sheet footer: the four keycaps "Ctrl Alt Shift R" overflow the row and the line "Start or stop from anywhere" is false on GNOME 46 Wayland (no GlobalShortcuts portal).
* The permissions page still lists the Camera ("Shows your webcam in the bubble") although Linux has no camera recording.
* The Studio's own window is in a recording of its screen (macOS captures it on purpose, REC-6.AC8).
* A real desktop, the GNOME top-bar Stop item, the KDE indicator, a tray host, 4K/60, real GPU, A/V sync by flash and beep were not looked at.

## Verdict

PARTIAL. In the headless GNOME session the app's Record sheet, banner, countdown, pause, stop, the first-start share dialog, a lost share, the library picture, the details page and the "nothing opens it" message work behind `CM_LINUX_RECORDING=1`, and an X11 session works with the banner (and, opted in, the floating HUD). Not shown: any real desktop or panel, the tray's recording state, the audio-only sheet, errors provoked inside the app, and the rule that a recording is never without a visible indicator cannot be guaranteed on a Wayland compositor that shows none.
