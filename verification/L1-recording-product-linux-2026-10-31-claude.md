# L1 report: screen and audio recording on Linux through the product path (daemon action, CLI)

- **Date:** 2026-10-31
- **Who:** Claude (run for the maintainer; nobody watched the screen; the portal consent was not asked because the restore token of the L0 run was copied into the test config folder)
- **Machine:** QEMU virtual machine on a MacBook Pro (Apple M4 Pro), 4 vCPUs shared with other jobs (load average 0.6 to 12 during the work), 8 GB, **aarch64**, Ubuntu 24.04.5, GNOME Shell 46 started with `--headless --wayland --virtual-monitor 1280x720` (software rendering, no `/dev/dri`, no `/dev/video*`), xdg-desktop-portal 1.18.4, xdg-desktop-portal-gnome 46.2, PipeWire 1.0.5 with WirePlumber. Audio: the "Dummy Output" sink (system audio) and a null `Audio/Source/Virtual` node `cm-test-mic` (microphone, silence).
- **Build:** release build of `cm-daemon` and `capturemann` (`cargo build --release --bins --no-default-features`, `CARGO_INCREMENTAL=0`) from the tree of commit `1c793c1` (the commit before this report). The VM copy is an rsync of the work tree (no `.git`).
- **FFmpeg:** `ffmpeg version 6.1.1-3ubuntu5` (the distribution's, GPL build with libvpx; development use only, not the product's bundled FFmpeg). The daemon found it on `PATH`.
- **Fixture:** `weston-simple-shm` animating in the headless session, the pointer moved in a circle through Mutter RemoteDesktop (`/tmp/wiggle.py`) so frames keep flowing, and for audio `pw-play` of a 12 s stereo file with a 100 ms 1 kHz beep at 1, 3, 5, 7 and 9 s into the file, started 1.5 s after `record start`. Scripts used (not stored in the repo): the run script started `cm-daemon` with `CAPTUREMANN_CONFIG_DIR`, `CAPTUREMANN_LIBRARY` and `CAPTUREMANN_SOCKET` pointing into `/home/dev/cm-wire-run`, a `settings.json` with `{"agents.tool_policy": {"start_recording": "allow"}, "recording.countdown_s": 0}` (a headless daemon has no confirmation window, so an agent could not start otherwise), and the token file `screencast-token` (mode 0600) in the config folder.

This is **not** real hardware: no GPU, no hardware encoder, 720p, a virtual 60 Hz monitor, simple content (low encode cost), a null microphone. It shows that the product path (`start_recording` -> `LinuxSources` -> portal + PipeWire source -> session clock -> software VP9 encoder, microphone and system audio on PipeWire -> bundle -> library) works end to end through the real daemon and CLI. It says nothing about 1080p/4K, DMA-BUF, VA-API/NVENC, other desktops, or a real microphone.

## Acceptance criteria

None claimed. This is the product wiring behind REC-1 to REC-4 and AUD-1/AUD-2 on Linux (`specs/platform-acceptance.md` rows stay open: the desktop shell, the HUD, window and region targets, the camera, the cursor track, hardware encoders and every real-hardware check are missing).

## Problems found

- The first stream-loss run showed that a dead producer looks like a still screen: the source sends an "unchanged" sample every 250 ms while no buffer arrives, so the stall watchdog stays quiet. Fixed for a removed node (registry `global_remove`); a stream that stays registered but stops sending (a hung compositor) is still indistinguishable from a quiet desktop and would record a frozen picture until the user stops it.
- The start answer and the confirmation text describe the plan: `display 1, 1920 x 1080 px, 30 fps, h264`, while the file is 1280x720 VP9. The portal's dialog picks the screen, so the size is only known after connecting. The start answer carries a warning saying so, and the manifest tells the truth. A saved last-stream size would make the plan closer.
- The manifest track details say `"codec": "vp9"` through `VideoEncoder::codec_name()`; `Codec` has no `Vp9` variant yet. **TODO(Codec::Vp9)** in `crates/cm-encode/src/encoder.rs`: when the other agent's `Codec::Vp9` lands, `used_plan` should carry it and `codec_name` goes away. `cursor: true` in the details now means "in the pixels", which is true.
- System audio: the first chunk produced a 21 ms resync and a -2229 ppm "drift" figure in the details in both runs that played the beeps; the example run did not. Not investigated.
- `needs_reopen` for the PipeWire audio sources (following a default-device change) is still not implemented, and a PipeWire daemon dying mid-recording is not handled for the audio tracks (untested).
- The popup of the portal's own dialog on a revoked token during an agent-started recording is the same risk as before (R4 in the plan): `start_recording` blocks up to the portal's own timeout (180 s), then answers an error.
- The bundled FFmpeg has no VP9 decoder: the product's editor and exporter cannot open these files yet (`packaging/`, D-R4).
- `capturemann devices` (text) prints "Screen recording permission: authorized" for a stored token; the truth behind it is "the desktop remembered the share", the portal can still ask again if the user revoked it.
- Recording tests with a restored token cannot show the first-run dialog path on this VM.

## Verdict

PARTIAL. The Linux screen + microphone + system audio recording works through the real `start_recording` / `stop_recording` actions and `capturemann record start/stop` in the headless GNOME VM, with the portal token reused, perfect constant frame rate, a playable VP9 file, 0.27 core of CPU at 720p30, and a clean stop when the shared screen disappears. Not done: the portal-closed and PipeWire-restart paths on a real session, 60 fps through the product path, A/V sync by flash and beep, a real microphone, any real GPU or desktop, window/region/camera/cursor track, hardware encoders, the HUD and the desktop app's recording UI.
